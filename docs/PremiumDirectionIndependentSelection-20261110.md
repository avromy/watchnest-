## Why A wins

A makes the entire approved collection a first-class destination while allowing a small useful resume/recent surface. Search, sorting, Favorites and Collections can serve both a child who remembers a title and a child who recognizes artwork. This works without requiring a Parent to organize hundreds of videos into child-understandable rooms first. Visible profile identity can remain separate from content filters.

For Parents, persistent Add videos plus actionable requests and child libraries fit a short phone session. The four labelled destinations provide stable return locations. Approval and assignment adjacent to a concrete item should reduce context switching without introducing B's split-pane selection and phone-sheet model. Counts must open useful work rather than merely decorate an overview.

Its premium character must come from artwork hierarchy, controlled density, precise typography, spacing, clear selected states and coherent warm materials. The written proposal's ivory/evergreen/amber vocabulary alone is insufficient evidence of visual quality. A must not become a generic dashboard with a renamed hero.

## Why the alternatives lose

**B has the strongest batch-curation interaction.** A selected item remaining visible through queue processing is useful for sustained Parent work, and one Browse surface avoids Home/Library duplication. However, the persistent child rail spends iPad portrait width on navigation, and younger children must interpret a filter workspace. Parent phone review introduces sheet opening, dismissal, result return, selection retention and focus restoration. Those costs affect the primary devices, not just implementation effort. B should be reconsidered only if observed recurring Parent sessions show batch curation dominates and the phone interaction is proven superior. Do not silently import its desk/sheet architecture into A.

**C has the clearest picture-led entry for younger children.** Large concrete Collection choices are distinctive and could work well in Simple mode. But collection-first navigation adds a choice and backtracking before playback, assumes useful family organization, and still needs All videos/search for large libraries and older children. The Parent task launcher is clear but makes the boundary between task entries and ongoing Library work less stable. C's strengths can inform large readable Collection covers within A's existing collection destination; they do not justify a new mandatory collection index or setup requirement.

## Binding conditions for A

1. **Home must earn a distinct purpose.** It contains a bounded useful resume/recent selection and direct retrieval shortcuts. Library is always the complete collection. Empty and Simple profiles must have a direct useful library/empty-state path; do not retain a welcome page or duplicate grid solely to preserve a Home concept.
2. **Retrieval remains immediate and deterministic.** Make All videos, search, sorting, Favorites and Collections findable. Search and filters must operate on approved library items; clear filter state and empty results must expose an obvious return to the full collection. Large-library review must test retrieval beyond the initially visible shelf.
3. **Discovery is unmistakably request-only.** Any child external-discovery destination must explain its request purpose before item action. Results cannot resemble currently playable approved tiles. Approval status, request feedback and return navigation need readable text, not color alone. No approval boundary may be relaxed to simplify the design.
4. **Parent overview starts with work.** Actionable pending requests and child-library tasks precede static totals or decoration. Keep one clear persistent Add videos action. No authenticated slogan, acquisition hero, promotional artwork collage, or repeated sales CTA. Confirm that each count and primary destination leads to the promised task.
5. **Phone task completion is the deciding Parent test.** Opening a request, inspecting the exact video, assigning a child, approving/rejecting and returning must keep context intelligible. Do not infer tap efficiency from a desktop screenshot. Preserve clear final feedback and predictable back behavior.
6. **Adapt layout to each device.** Child iPad portrait and landscape must preserve legible titles, obvious profile ownership and 44px essential targets without an unnecessarily wide rail. Parent phone uses reachable labelled navigation and stacked tasks. Desktop adds related-work columns without inventing a different hierarchy.
7. **Keep accessibility and security noncompensable.** Keyboard/focus order, reduced motion, readable status and error feedback, protected Parent transitions, sibling isolation, individual-video approval, ingestion and timers remain required. Reusing routes or APIs is not security evidence. Any affected flow needs exact-candidate requalification.
8. **Freeze one direction, then test the result.** Build A under these conditions. Do not present a three-way Founder choice, hybridize the navigation models casually, or treat this receipt as rendered acceptance. A material IA change after this freeze requires renewed independent assessment of the affected decision.

## Required evidence after implementation

Bind later evidence to the exact tested candidate. Required checks include child approved-library retrieval at a representative hundreds-item scale; profile switch and sibling isolation; request-only discovery feedback; Parent phone intake/request review/assignment/approval and return; child iPad portrait/landscape; keyboard/focus and essential targets; protected Parent access; ingestion/timer/player containment regressions. Rendered visual quality and genuinely independent cold review remain separate gates under current project authority. A polished screenshot cannot stand in for these flows, and a functional flow cannot establish visual excellence.

**Frozen decision: proceed with A and its eight conditions. No implemented PASS claimed.**
